# Dockerização dos microservices

Este repositório usa três abordagens diferentes de containerização para demonstrar formas distintas de empacotar aplicações Spring Boot. Cada microservice adota uma estratégia própria:

- `accounts`: Dockerfile manual
- `cards`: Jib Maven Plugin
- `loans`: Spring Boot Buildpacks com `build-image`

Essa divisão é útil porque mostra, na prática, os principais caminhos para gerar imagens Docker em projetos Java modernos.

## Visão geral

| Microservice | Abordagem | Onde está configurado | Como a imagem é gerada |
| --- | --- | --- | --- |
| `accounts` | Dockerfile tradicional | `accounts/Dockerfile` | `docker build` após gerar o `.jar` |
| `cards` | Jib | `cards/pom.xml` | `mvn jib:dockerBuild` ou `mvn jib:build` |
| `loans` | Spring Boot Buildpacks | `loans/pom.xml` | `mvn spring-boot:build-image` |

## 1. Accounts: Dockerfile manual

O microservice `accounts` usa a abordagem mais tradicional. Existe um arquivo [`accounts/Dockerfile`](../accounts/Dockerfile) com instruções explícitas para montar a imagem:

```dockerfile
FROM eclipse-temurin:21-jdk

LABEL "org.opencontainers.image.authors"="thomazllr.com"

COPY target/accounts-0.0.1-SNAPSHOT.jar accounts-0.0.1-SNAPSHOT.jar

ENTRYPOINT ["java", "-jar", "accounts-0.0.1-SNAPSHOT.jar"]
```

### Como funciona

Primeiro o projeto gera o artefato `.jar` com Maven. Depois o Docker copia esse arquivo para dentro da imagem e define o comando de inicialização da aplicação.

Exemplo de fluxo:

```bash
cd accounts
mvn clean package
docker build -t thomazllr/accounts:s4 .
docker run -p 8080:8080 thomazllr/accounts:s4
```

### Vantagens

- Controle total sobre a imagem final.
- Fácil de entender para quem já trabalha com Docker.
- Permite customizações finas de sistema operacional, camadas, variáveis de ambiente e processo de startup.
- É uma boa opção quando a aplicação precisa de ajustes específicos no container.

### Desvantagens e trade-offs

- Exige mais manutenção manual.
- O time precisa cuidar diretamente da imagem base, do `COPY`, do `ENTRYPOINT` e de possíveis otimizações.
- Se o Dockerfile não for bem estruturado, o build pode ficar menos eficiente.

### Quando essa abordagem faz mais sentido

Ela é ideal quando o projeto precisa de liberdade total sobre a montagem da imagem ou quando a equipe quer explicitar cada etapa da containerização.

## 2. Cards: Jib Maven Plugin

O microservice `cards` usa o plugin Jib, configurado no [`cards/pom.xml`](../cards/pom.xml):

```xml
<plugin>
    <groupId>com.google.cloud.tools</groupId>
    <artifactId>jib-maven-plugin</artifactId>
    <version>3.5.2</version>
    <configuration>
        <to>
            <image>thomazllr/${project.artifactId}:s4</image>
        </to>
    </configuration>
</plugin>
```

### Como funciona

O Jib gera a imagem diretamente a partir do projeto Java, sem exigir um `Dockerfile`. Ele entende a estrutura da aplicação, separa dependências, recursos e classes em camadas e monta a imagem de forma otimizada.

Exemplo de fluxo:

```bash
cd cards
mvn clean compile jib:dockerBuild
```

Ou, para enviar diretamente a um registry:

```bash
mvn clean compile jib:build
```

### Vantagens

- Não precisa escrever Dockerfile.
- Gera imagens em camadas de forma inteligente, melhorando reaproveitamento de cache.
- Reduz erros manuais no processo de containerização.
- Integra muito bem com pipelines Maven e CI/CD.
- Costuma acelerar o ciclo de build em aplicações Java.

### Desvantagens e trade-offs

- Há menos liberdade do que em um Dockerfile totalmente manual.
- Customizações muito específicas podem ser mais trabalhosas.
- A equipe precisa entender a convenção do Jib e seus parâmetros.

### Quando essa abordagem faz mais sentido

Ela é uma escolha forte para times que querem produtividade, padronização e builds mais simples, especialmente em aplicações Java que não exigem grande customização da imagem.

## 3. Loans: Spring Boot Buildpacks com `build-image`

O microservice `loans` usa o plugin padrão do Spring Boot com suporte a Buildpacks. A configuração está no [`loans/pom.xml`](../loans/pom.xml):

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <image>
            <name>thomazllr/${project.artifactId}:s4</name>
        </image>
    </configuration>
</plugin>
```

### Como funciona

Nesse caso, o Maven usa o objetivo `spring-boot:build-image`, que delega a criação da imagem aos Cloud Native Buildpacks. O processo detecta automaticamente que a aplicação é Spring Boot/Java, escolhe uma base compatível e gera a imagem pronta para execução.

Exemplo de fluxo:

```bash
cd loans
mvn clean spring-boot:build-image
```

### Vantagens

- Processo muito simples e bastante integrado ao ecossistema Spring Boot.
- Remove a necessidade de manter Dockerfile manual.
- Segue uma convenção moderna para empacotamento de aplicações cloud native.
- Facilita padronização entre serviços Spring.
- Reduz esforço operacional para gerar imagens seguras e consistentes.

### Desvantagens e trade-offs

- Menor nível de controle em comparação ao Dockerfile manual.
- O resultado depende mais das convenções dos Buildpacks.
- Para cenários muito específicos, pode ser necessário customizar a configuração do plugin ou mudar de abordagem.

### Quando essa abordagem faz mais sentido

Ela funciona muito bem quando o foco é simplicidade, aderência ao ecossistema Spring e geração rápida de imagens com pouca configuração manual.

## Comparação prática entre as três abordagens

### Dockerfile manual (`accounts`)

- Melhor quando o objetivo é controle.
- Mais indicado para cenários com requisitos especiais de imagem.
- Exige mais trabalho operacional.

### Jib (`cards`)

- Melhor quando o objetivo é produtividade no build Java.
- Muito útil em pipelines CI/CD.
- Evita Dockerfile e cria camadas otimizadas automaticamente.

### Spring Boot Buildpacks (`loans`)

- Melhor quando o objetivo é simplicidade com padrão Spring.
- Ótimo para subir imagens rapidamente com configuração mínima.
- Forte aderência ao modelo cloud native.

## Conclusão

Os três microservices mostram uma evolução natural de estratégias de dockerização:

1. `accounts` apresenta a base tradicional com Dockerfile manual.
2. `cards` mostra uma alternativa mais automatizada com Jib.
3. `loans` adota uma abordagem ainda mais integrada ao Spring Boot com Buildpacks.

Na prática, nenhuma abordagem é universalmente melhor. A escolha depende do nível de controle desejado, do esforço de manutenção aceitável e do grau de automação esperado no fluxo de build e deploy.
